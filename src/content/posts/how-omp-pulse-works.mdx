My brother and I built [OMP Pulse](https://github.com/JulianCodespoti/omp-pulse) because driving a terminal coding agent over SSH on a phone screen is miserable. It's a single Rust binary (`tokio` + `axum`) with the React client compiled straight into the executable. You can run it on your laptop over Tailscale, or run the exact same binary inside an unrooted Android APK when your laptop is shut.

Serving the web app is the easy part. Keeping memory flat, history snappy, and cellular traffic light when you have 3,000+ past sessions on disk is where things get interesting. Every number below comes from our benchmark harness (`docs/internals/performance.md`) against a corpus of 3,365 sessions.

## Browsing in 14 MB with a lazy worker pool

The Rust daemon itself uses about 14 MB of RAM. Almost all the real memory sits inside the coding-agent child processes (`omp --mode rpc-ui`). Each worker takes 281 MB at rest, spikes to 493 MB while booting, and needs 1.3 to 2.7 seconds before it's ready.

At actual scale, a single worker is 20 times larger than the daemon. If tapping a conversation in the sidebar booted a worker right away, skimming through five chats would burn 1.4 GB before you typed anything.

So Pulse splits reading from running. Opening a chat reads directly from disk with zero workers alive (14 MB total). The moment you tap the reply box, the phone fires `POST /api/prewarm` so the worker starts booting while you're still typing your prompt.

Workers also share a 3-slot pool (891 MB under a 12-chat burst instead of 3.4 GB). Once all three slots are warm, replying in a fourth chat retargets the oldest idle worker (`switch_session`) in 59 ms instead of paying another two-second cold boot. Idle workers get reaped after 15 minutes, and any worker whose RSS creeps past 700 MB gets recycled cleanly between turns.

## Opening a 44 MB chat in 0.59 ms

Conversations are stored as append-only JSONL files. After a long debugging session full of test output, a single file can pass 44 MB. When you open that chat on your phone, you only care about the last screen of messages at the bottom.

Reading a 44 MB file from byte zero takes 36.4 ms and drags the whole history through memory just to return 70 KB. Instead, Pulse seeks straight to EOF and reads small chunks backward until it has enough records for page 1. On our 44 MB fixture, that drops first-screen load from 36.4 ms down to 0.59 ms (62x faster).

<TailRaceFigure client:visible />

Two small caches cover everything else. If you scroll up into older messages, the parsed session tree is cached by `(path, size, mtime)`, dropping repeat reads from 105 ms cold to 17 microseconds cached. And the session sidebar is backed by a shared stale-while-revalidate index (`Arc<str>` + content-addressed `ETag`), which took polling 3,365 sessions from 134.2 ms cold down to 0.74 ms and a 300-byte `304 Not Modified`.

## Streaming live tokens at one-tenth the bandwidth

While an agent is writing a reply, live tokens stream over a WebSocket. The naive version sends the whole growing reply on every update. On a measured 4,228-character turn, that turned 4 KB of text into 244 KB on the wire (57.8x amplification).

Instead, the daemon diffs each frame against the previous one and sends a <Cue tone="sage">prefix delta</Cue>: keep `k` UTF-16 code units, append the new tail. Counting `k` in UTF-16 matches `String.prototype.slice` in the browser so emojis never get split across surrogate pairs, and replacing the suffix handles trailing whitespace edits cleanly. That same 4,228-character turn drops from 244 KB to 25 KB (9.7x smaller).

Each delta carries the sequence number (`base_seq`) it builds on. Fast phones stay on tiny deltas. If a phone drops packets or joins mid-stream, its sequence number won't match, so the hub sends one clean snapshot and picks right back up on deltas for the next token. ## Keeping memory flat when your phone sleeps or loses signal

A background watcher tails active session files and fans updates out to connected phones. Mobile connections are messy in two specific ways: phones go through tunnels, and locked phones keep their WebSocket open in your pocket.

To handle locked phones, the hub tracks only visible clients that actually have queue headroom (`has_audience`). As soon as your screen turns off, the watcher parks completely instead of waking every 250 ms, and queues one refresh for when you unlock.

Tunnels were trickier. Each client queue caps both frame count and total bytes. Our first attempt cleared the queue on overflow and pushed a tiny 200-byte `resync` frame. In a slow-consumer test with a 150 MB append, that queue oscillated 123 times and spiked daemon RSS by +320 MB, because clearing the queue immediately restored headroom and told the watcher to keep reading.

Flipping a <Cue tone="sage">stall latch</Cue> fixed it. Once a queue overflows, the intake gate stays shut until the phone actually reconnects and drains, holding RSS growth on that 150 MB burst at +0 MB. Once a burst settles, watcher buffers over 256 KB are dropped instead of pinned, and on Linux glibc the maintenance loop calls `malloc_trim` so freed heap arenas go straight back to the OS.

## One writer on disk and pure-Rust push

Two smaller pieces finish the loop between laptop and phone.

First, terminal `omp` rewrites its JSONL file wholesale from memory, so two processes writing to the same file will clobber each other. Before spawning a worker, Pulse checks a sidecar lock file, live process arguments, and open file descriptors. If your desktop terminal already owns the chat, phone prompts route through the desktop extension instead of starting a second writer. Both screens stay live at token level, and only one process touches disk.

Second, we didn't want a cloud relay or OpenSSL in the build tree just to send push notifications when a long run finishes. Pulse implements RFC 8291 (`aes128gcm`) and VAPID ES256 signing in pure Rust (`p256`, `hkdf`, `sha2`, `aes-gcm`). Google, Apple, and Mozilla's push relays only ever see ciphertext, and with zero C crypto dependencies, the whole binary cross-compiles to static `aarch64-unknown-linux-musl` for Android in about 20 seconds.
