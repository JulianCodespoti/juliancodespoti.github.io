A year ago, every agent architecture diagram looked like a startup org chart. You had a Planner talking to a Researcher, who briefed a Coder, who handed a PR to a QA Reviewer. It looked great on a slide.

Then people actually ran these setups on real repos and noticed something awkward: a single model in a 200-line loop usually finished faster, cost a fraction as much, and made fewer weird mistakes than the five-agent version.

I don't think multi-agent setups are useless. Most of them just split work along human job titles instead of along actual system boundaries. Once you look at what happens to prompt caches, context windows, and error rates, it gets pretty obvious where extra agents hurt and where they pull their weight.

## The handoff tax

Passing work from Agent A to Agent B looks like a thin arrow on a whiteboard. On the wire, you pay for it three ways.

First, Agent B starts cold. It has its own system prompt and its own message history, so the provider can't reuse Agent A's KV prefix cache. You pay full prefill latency and full input cost all over again.

Second, Agent A has to compress everything it learned into a handoff message. That summary almost always drops the small details that actually mattered: the weird edge case in line 42, the two approaches it already tried and ruled out, the exact flag that broke the build.

Third, because that handoff is lossy, Agent B spends its first couple of turns re-reading the same files Agent A just had open.

## When a second agent is worth it

If handoffs are that expensive, why spawn another agent at all?

The best reason I've found is keeping noisy reads out of your main context. Say you're chasing down a lock bug in a big repo and you just need an answer to one question: where is this mutex acquired?

If the main agent runs six greps and opens twelve files itself, 40,000 tokens of raw search output and unrelated code get glued into its history for the rest of the session. Every edit it makes after that drags those 40K tokens along for the ride.

A short-lived, read-only <Cue tone="teal">subagent</Cue> flips that around. Spin it up with one narrow question, let its throwaway window eat all 40K tokens of grep noise, take back a 400-token answer with file paths and line numbers, and throw the subagent away. Your main loop stays light and its prefix cache stays intact.

## Why chains drift (and why a fresh pair of eyes fixes it)

The other problem with long agent relays is plain multiplication. If each handoff preserves 88% of what you actually asked for, five hops in a row leave you with `0.88^5`, or roughly 53%. Small ambiguities compound fast when nobody goes back to check the original source of truth.

There is one place where starting from a blank context actually helps, though: review.

When a single agent writes 200 lines of code and you ask it to double-check its own work in the same thread, it's reading its own justification right above the diff. It already convinced itself that its assumptions hold. Hand the diff and the test suite to an independent <Cue tone="sage">verifier</Cue> with an empty context window instead, and it treats the code like a stranger's PR. It catches skipped edge cases and half-wired paths the original loop glossed right over.

## What I actually use

Most tasks don't need orchestration at all. If I'm fixing a bug or building a self-contained feature, I just run one agent with a tight compiler and test loop. It's cheaper, faster, and much easier to debug when it goes sideways.

I skip role-playing swarms completely. Splitting planning, coding, and reviewing into chatty personas mostly burns tokens while playing telephone with your own codebase.

On bigger tasks where a single window starts to drown, the shape that holds up is simple: one main agent owns the plan and all edits, disposable read-only subagents handle broad codebase searches, and a fresh-context verifier checks the finished diff before wrapping up.
