A year ago, every agent architecture diagram looked like a startup org chart. You had a Planner talking to a Researcher, who briefed a Coder, who handed a PR to a QA Reviewer. It looked clean on a slide.

Then people actually ran these setups on real repos and hit an awkward result: a single model in a 200-line loop almost always finished faster, cost a fraction as much, and made fewer weird mistakes than the four-agent version.

I don't think multi-agent setups are useless. Most of them just split work along human job titles instead of along actual system boundaries. Look at the token geometry of a handoff and the reason becomes obvious in seconds.

## The geometry of the handoff tax

Passing work from Agent A to Agent B looks like a thin arrow on a whiteboard. Under the hood, it breaks the single biggest optimization modern LLM serving gives you: **prefix caching**.

A <Cue tone="sage">single agent</Cue> doing an eight-turn task pays cold prefill once on turn 1. On turns 2 through 8, its prefix stays warm and cached at 0.1x cost, so each step only pays full price for the thin sliver of new tokens it just added.

Now split that same eight-turn task across a Planner, a Researcher, a Coder, and a Reviewer. Every time work crosses a role boundary, the new agent has a different system prompt and no shared KV prefix. Worse, because the handoff summary drops small details, the next agent usually re-reads the same files to orient itself. Instead of one warm staircase, you pay for four separate <Cue tone="crimson">cold starts</Cue>.

There is a second hidden cost to long chains: plain error multiplication. If each lossy handoff preserves 88% of your original constraints, five hops in a row leave you with `0.88^5`, or roughly 53%. Small ambiguities compound fast when nobody is looking at the original source of truth anymore.

## When a second agent actually pays off

If handoffs are that expensive, why ever spawn a second agent?

The strongest reason is **context hygiene**. Say you're tracking down a subtle lock bug in a big monorepo and need the answer to one narrow question: where is this mutex acquired?

If the main agent runs six greps and opens twelve files itself, tens of thousands of tokens of raw search output land straight inside its working window. Even if everything fits well under a 200K token limit, those irrelevant log lines drown out your actual spec and stay pinned in history for every edit that follows.

A short-lived, read-only subagent flips the math. You spin up a throwaway window, let it absorb all the raw grep noise, extract just the <Cue tone="teal">four relevant answers</Cue> with file paths and line numbers, hand them back to the main agent, and discard the subagent completely.

## The second exception: a fresh pair of eyes

There is one other place where a blank context window beats a warm one: final verification.

When a single agent writes 200 lines of code and you ask it to review its own diff in the same thread, its context is packed with its own rationalizations right above the code. It already talked itself into its assumptions. Handing the finished diff and the test suite to an independent verifier with an empty context window strips out writer bias. It reads the diff like a stranger's PR and catches skipped edge cases and half-wired paths the original loop glossed right over.

## What I actually run

For focused bugs and small features, I just use one agent with a tight compiler and test loop. It keeps one warm cache, skips handoff drift, and stays trivial to debug.

I avoid role-playing swarms completely. When a task gets big enough that one context window starts drowning, the layout that actually works is simple: one main agent owns the plan and every file edit, disposable read-only subagents handle noisy repo searches, and one fresh-context verifier checks the finished diff before wrapping up.
