[OMP Pulse](https://github.com/JulianCodespoti/omp-pulse) lets you drive terminal coding agents from your phone over Tailscale, or run the exact same daemon locally inside an unrooted Android APK when your laptop is closed.

The whole server is a single Rust binary (`tokio` + `axum`) with the React web client compiled straight into the executable. On a laptop or phone with thousands of past conversations, the hard part is not serving HTTP; it is keeping memory flat, history instant, and mobile data light while heavy coding-agent workers run underneath.

Here is how the pipeline works from top to bottom, with every measurement pulled from our benchmark corpus of 3,365 real-sized sessions.

## 1. Browsing in 14 MB with a lazy worker pool

The Rust daemon itself uses about **14 MB** of RAM. All the heavy memory lives inside the coding-agent child processes (`omp --mode rpc-ui`): each worker takes roughly **281 MB** at rest, peaks around **493 MB** while booting, and takes **1.3 to 2.7 seconds** to start.

If opening a conversation on your phone spawned a worker immediately, flipping through five chats would burn over **1.4 GB** of RAM before you typed a single word.

Instead, OMP Pulse separates **reading** from **running**:

- **Reading is free:** Opening a chat reads the session file directly from disk with zero workers running (`14 MB` total).
- **Pre-warming on intent:** The moment you tap the reply box to start typing, the phone calls `POST /api/prewarm`. The worker boots in the background while you compose your prompt, hiding startup latency behind human typing speed.
- **Capped pool with hot retargeting:** Workers share a pool capped at **3 slots** (`891 MB` under a 12-chat burst instead of `3.4 GB`). When all slots are warm, replying in a new chat **retargets** an idle worker (`switch_session`) in **59 ms** instead of paying another 2-second cold boot. Idle workers are reaped after 15 minutes, and any worker whose RSS drifts past **700 MB** is recycled cleanly between turns.

## 2. Opening a 44 MB chat in 0.59 ms

Conversations are stored as append-only JSONL files that can grow past **44 MB** after long debugging sessions with tool output. When you tap a chat on your phone, you only need the most recent screen of messages at the bottom.

Reading a 44 MB file from byte zero takes **36.4 ms** and pulls the entire history through memory just to return **70 KB** of recent turns.

OMP Pulse skips straight to the end of the file and reads small chunks backward until it has enough messages to fill page 1. That cuts the first-screen load on a 44 MB session from **36.4 ms down to 0.59 ms** (**62x faster**).

Two small caches keep the rest of the UI just as fast:

- **Parsed session cache:** If you scroll upward into older history, the parsed message tree is cached by `(path, size, mtime)`. Subsequent page loads drop from **105 ms cold to 17 microseconds cached**.
- **Stale-while-revalidate session index:** Listing 3,365 conversations used to take **134.2 ms** cold. One shared index now serves every query from a cached `Arc<str>` with a content-addressed `ETag`, dropping steady-state polls to **0.74 ms** and **300-byte `304 Not Modified`** responses.

## 3. Streaming live tokens at one-tenth the bandwidth

While an agent is actively writing a reply, tokens stream over a WebSocket. The simplest way to keep the phone UI in sync is to send the whole growing reply on every update, which turns a 4,228-character message into **244 KB** of repeated wire traffic (`57.8x` amplification).

Instead, the daemon compares each new frame against the previous one and sends only a compact <Term tone="sage">prefix delta</Term>: keep `k` UTF-16 code units, append the new suffix. Measuring `k` in UTF-16 units matches JavaScript's `String.prototype.slice` directly so emojis are never split mid-character, and suffix replacement handles trailing whitespace normalization cleanly.

On the exact same 4,228-character turn, wire traffic drops from **244 KB to 25 KB** (**9.7x smaller**).

<StreamWireScene client:visible />

Every delta carries the sequence number (`base_seq`) it builds on. Fast clients stay on tiny deltas; if a phone briefly drops packets or joins mid-stream, its sequence number will not match and the hub automatically sends one clean full snapshot before resuming deltas on the next token.

## 4. Keeping memory flat when your phone sleeps or loses signal

A background file watcher tails active chats and fans updates out to connected phones. Mobile networks introduce two tricky situations: phones frequently lose signal in tunnels, and locked phones keep their WebSocket open in your pocket.

OMP Pulse keeps daemon memory completely flat with three layers:

1. **Audience-aware sleeping:** The hub tracks which sockets are actually visible and ready to receive (`has_audience`). The moment you lock your phone, the watcher parks completely instead of waking every 250 ms, and queues a single refresh for when your screen turns back on.
2. **Byte-capped queues with a stall latch:** Each client queue caps both frame count and total bytes. If a phone goes offline during a **150 MB** build log, simply clearing the queue makes headroom again so the watcher keeps reading and spikes memory by **+320 MB**. Instead, overflowing flips a <Term tone="sage">stall latch</Term> that closes the intake valve until the phone drains, holding RSS growth at **+0 MB**.
3. **Returning memory to the OS:** Once a heavy burst finishes, oversized watcher buffers above 256 KB are dropped rather than pinned, and on Linux glibc the maintenance loop calls `malloc_trim` so freed heap arenas return to the operating system immediately.

## 5. One writer on disk and private push without cloud relays

Two architectural choices finish the loop between laptop and phone.

**Single-writer routing:** A terminal `omp` session rewrites its JSONL file from memory, so two processes writing to the same file would clobber each other. Before spawning a worker, the daemon checks a sidecar lock file, live process arguments, and open file descriptors. If your desktop terminal already owns the chat, phone prompts route straight through the desktop extension instead of spawning a second writer, keeping both screens live at token level with a single owner on disk.

**Pure-Rust encrypted push:** When an agent finishes a long run while your phone is locked, you want a notification without routing your prompts through a custom cloud server or bundling OpenSSL into cross-compiled mobile builds.

OMP Pulse implements RFC 8291 Web Push (`aes128gcm`) and VAPID ES256 signing directly in pure Rust (`p256`, `hkdf`, `sha2`, `aes-gcm`). The daemon seals each <Term tone="sage">notification</Term> into <Term tone="copper">encrypted bytes</Term> before handing it to Google, Apple, or Mozilla's push relay, so the relay never sees your code or replies.

Because there are zero C cryptography dependencies in the build tree, the entire server cross-compiles cleanly to Linux, macOS, Windows, and static `aarch64-unknown-linux-musl` for Android in about 20 seconds.
