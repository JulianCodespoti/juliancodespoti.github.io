When you send a one-line reply to a coding agent on turn 18, it feels like sending a short message. It isn't. LLM APIs are stateless, so your harness re-sends the whole conversation from byte zero on every turn: system instructions, every tool definition, every file the agent opened, every stack trace, and every reply so far.

Once you see what actually sits inside that 200,000-token buffer, a lot of strange agent behavior suddenly makes sense. You see why a single verbose test failure makes the rest of your session sluggish, why plugging in 40 MCP servers quietly wrecks quality, and why summarizing old turns too often can make your API bill go up.

## Where the tokens actually go

In a real coding session, the words you type are usually less than 5% of the prompt. Almost the entire window is <Cue tone="sage">file reads</Cue> and raw <Cue tone="copper">tool output</Cue>.

Run a noisy `npm test` or a verbose Rust compile error without truncating it, and you can dump 20,000+ tokens of stack traces straight into history in one shot. Because every turn after that replays the same message array, that one ugly log hangs around for the rest of the chat.

Compare that to sending a disposable subagent to search a dozen files in its own throwaway window and return a 450-token summary. Same answer, two orders of magnitude less junk stuck in your main prompt.

## The tax you pay before turn 1

Before the model reads a single line of your code, the harness has to explain every tool it can call as JSON inside the prompt prefix. A normal tool schema with descriptions, parameter types, and enums runs roughly 400 to 500 tokens.

Give the agent six clean primitives (`read`, `edit`, `write`, `grep`, `find`, `bash`) and your tool block sits around 2.7K tokens. Wire up 50 MCP tools "just in case" and you're shipping 22.5K tokens of schema on every single turn before anyone says hello.

## Prefix caching (and how one byte breaks it)

If providers had to recompute attention over 60,000 tokens from scratch on every turn, coding agents would be too slow and too expensive to use. Instead, inference servers cache the KV state of the leading prefix of your prompt.

As long as you only append new messages to the end, the server reuses that cached prefix at roughly a tenth of the normal input price and skips almost all prefill work.

The catch is that KV states depend on every token before them, so matching is strictly prefix-based. Change one byte near the front, like putting a ticking `Current time: 14:03:22` in the system prompt or dynamically registering an MCP tool halfway through a chat, and every token after that point turns into a <Cue tone="crimson">cache miss</Cue>. A few simple harness habits save a surprising amount of money here. Keep the system prompt completely static (if the model needs the current time or git status, drop it into the latest user turn instead). Freeze the tool list for the life of a session. And treat the message array as append-only while you're working.

## Why compacting too early raises your bill

When a thread gets long, the obvious fix is to summarize older turns every few steps so the prompt stays small.

The problem is what that does to your prefix cache. Rewriting turns 1 through 6 into a fresh summary edits the front of the conversation, which invalidates everything after it. If you do that every few turns, you end up paying full uncached prefill over and over again.

Keeping the prefix untouched and capping noisy tool outputs before they ever hit history works much better in practice. Truncate giant logs to the head and tail, offload broad searches to subagents, and save full compaction for when you're genuinely running out of room. Most of the gap between a sluggish, expensive agent and a snappy one comes down to this. Keep the tool list lean and fixed, don't touch the front of the prompt, bound tool outputs before they land in history, and let disposable subagents take the hit for noisy searches.
